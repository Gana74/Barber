# KODA.md — Инструкции для AI-ассистента

## Обзор проекта

**Название:** Barber Telegram Bot

**Тип:** Telegram-бот для записи клиентов

**Технологический стек:**

- Node.js 18+
- Telegraf 4.x — фреймворк для Telegram-ботов
- telegraf-session-local — локальное хранение сессий
- Google Sheets API (googleapis) — хранение данных
- node-cron — планировщик задач для напоминаний
- dayjs + плагины (utc, timezone) — работа с датами и таймзонами
- dotenv — управление переменными окружения

**Архитектура:** Модульная, с разделением на сервисы (логика) и бот (UI/взаимодействие).

## Архитектура и зависимости модулей

### Точка входа (`index.js`)

1. Инициализирует конфиг через `initConfig()`
2. Создаёт сервис Google Sheets через `createSheetsService(config)`
3. Создаёт бота через `createBot({ config, sheetsService })`
4. Настраивает напоминания через `setupReminders()`
5. Запускает бота через `bot.launch()`

**Глобальные обработчики ошибок:**

- `unhandledRejection` — перехватывает необработанные отклонённые промиссы, специально обрабатывает ошибки Telegram API (403, 429, 400) без завершения процесса
- `uncaughtException` — перехватывает необработанные исключения, для ошибок Telegram API не завершает процесс, для критических ошибок — завершает с кодом 1

Эти обработчики предотвращают крах бота при ошибках отправки сообщений заблокировавшим пользователям.

### Сервис Google Sheets (`src/services/googleSheets.js`)

**Ответственность:** Все операции чтения/записи в Google Sheets.

**Ключевые методы:**

- `ensureSheetsStructure()` — создаёт листы и заголовки при первом запуске, автоматически выполняет миграцию старых записей в архив
- `getDaySchedule(dateStr)` — возвращает расписание и записи на день (с in‑memory кэшем, читает только активные записи)
- `appendAppointment(appointment)` — добавляет новую запись в активные
- `updateAppointmentStatus(id, status, meta)` — обновляет статус записи (ищет в активных и архиве). При завершении записи (статус "исполнено") автоматически обновляет поле `Последняя_запись_UTC` в таблице клиентов
- `getTimezone()` — получает таймзону из настроек таблицы
- `archiveOldAppointments(monthsToKeep)` — переносит записи старше указанного периода в архив
- `migrateExistingDataToArchive(monthsToKeep)` — однократная миграция существующих данных в архив

**Кэширование:**

- Простой in‑memory кэш по датам (`dayCache`) с TTL ~30 минут. Сбрасывается при изменении записей через `invalidateDayCache()` и периодически чистится фоновой задачей (ежечасная cron‑очистка устаревших ключей).
- Кэш рабочих часов (`workHoursCache`) также имеет TTL ~30 минут и обновляется при обращении и/или при фоновой очистке.

**Система архивирования:**

- **Разделение данных:** Записи разделены на активные (лист `Записи`, последние 2 месяца) и архивные (лист `Записи_Архив`, старше 2 месяцев)
- **Оптимизация производительности:** Клиентские методы (`getDaySchedule()`, `getAppointmentsByDate()`, `getAllActiveAppointments()`) читают только из активных записей (диапазон A2:Q500 вместо A2:Q2000), что ускоряет работу в 3-5 раз
- **Методы поиска:** `getAppointmentById()`, `getAppointmentByCancelCode()`, `updateAppointmentStatus()` ищут сначала в активных, затем в архиве
- **Админские методы:** `getCompletedAppointments()`, `getCancelledAppointmentsInPeriod()`, `getAllAppointmentsForClient()` объединяют данные из обоих листов для полной истории
- **Оптимизированные методы:** `getClientsFor28DayReminder()` использует поле `Последняя_запись_UTC` из таблицы клиентов как основной источник данных, без перебора всех записей (O(n) вместо O(n\*m))
- **Автоматическая ротация:** Ежемесячно в 3:00 ночи (1-го числа) записи старше 2 месяцев автоматически переносятся в архив
- **Автоматическая миграция:** При первом запуске после обновления существующие записи старше 2 месяцев автоматически переносятся в архив

**Структура таблицы:**
| Лист | Колонки |
|------|---------|
| `Настройки` | Ключ, Значение |
| `Расписание` | Дата, День*недели, Время*начала, Время*окончания, Обед*начало, Обед*окончание |
| `Блокировка времени` | Дата, Время*начала, Время*окончания, Статус, Услуга, Примечание |
| `Записи` | ID*записи, Создано*UTC, Услуга, Цена, Дата, Время*начала, Время*окончания, Имя*клиента, Телефон, Username*Telegram, Комментарий, Статус, Код*отмены, Telegram*ID, Исполнено_UTC, Отменено_UTC |
| `Записи*Архив`| ID*записи, Создано_UTC, Услуга, Цена, Дата, Время*начала, Время*окончания, Имя*клиента, Телефон, Username*Telegram, Комментарий, Статус, Код*отмены, Telegram*ID, Исполнено_UTC, Отменено_UTC |
|`Клиенты` | ID*клиента, Первое*посещение_UTC, Telegram_ID, Username_Telegram, Имя, Телефон, Последняя*запись*UTC, Всего\*записей |

### Утилита безопасной отправки сообщений (`src/utils/safeMessaging.js`)

**Ответственность:** Безопасная отправка сообщений с обработкой ошибок Telegram API.

**Ключевые функции:**

- `safeSendMessage(bot, chatId, text, options)` — безопасная отправка текстового сообщения
- `safeSendPhoto(bot, chatId, photo, options)` — безопасная отправка фото
- `safeReply(ctx, text, extra)` — безопасный ответ через ctx.reply
- `isBlockedError(err)` — проверка, является ли ошибка блокировкой бота (403)
- `isRateLimitError(err)` — проверка, является ли ошибка превышением лимита (429)

**Обрабатываемые ошибки:**

- **403 Forbidden** — пользователь заблокировал бота (логируется как предупреждение, не критично)
- **400 Bad Request** — неверный запрос (логируется как предупреждение)
- **429 Too Many Requests** — превышен лимит запросов (логируется с информацией о времени повтора)
- **Другие ошибки** — логируются с деталями

**Использование:** Все критические отправки сообщений в боте (напоминания, уведомления менеджеру, рассылки) используют эти функции для предотвращения краха процесса при ошибках Telegram API.

### Сервис бронирования (`src/services/booking.js`)

**Ответственность:** Бизнес-логика записи — услуги, генерация слотов, проверка пересечений.

**Справочник услуг:**
| Ключ | Название | Длительность |
|------|----------|--------------|
| `MEN_HAIRCUT` | Мужская стрижка | 60 мин |
| `BEARD` | Оформление бороды | 30 мин |
| `BUZZCUT` | Стрижка под машинку | 30 мин |
| `WOMEN_HAIRCUT` | Женская стрижка | 60 мин |

**Статусы:**

- `активна` (ACTIVE)
- `отменена` (CANCELLED)
- `исполнено` (COMPLETED)
- `заблокировано` (BLOCKED)

**Ключевые методы:**

- `getAvailableSlotsForService(serviceKey, dateStr)` — возвращает доступные слоты
- `bookAppointment({ serviceKey, dateStr, timeStr, client, comment })` — создаёт запись
- `cancelAppointment(id, telegramId)` — отменяет запись (проверка владельца)

**Ограничение записей:**

- Система ограничивает количество активных записей для одного пользователя: **не более 3 активных записей на любые даты**
- Проверка выполняется в `bookAppointment()` перед созданием записи
- Используется `getAllActiveAppointments()` для получения всех активных записей
- Пользователь идентифицируется по `telegramId`, `chatId` или `phone` (проверяются все доступные идентификаторы)
- При превышении лимита возвращается `{ ok: false, reason: "limit_exceeded", existingCount, existingAppointments }`
- Сообщение об ошибке отображается в сцене бронирования (`bookingScene.js`)

**Логика генерации слотов:**

- Шаг 15 минут
- Учитывает blocked-слоты из листа `Блокировка времени`
- Учитывает существующие активные записи
- Не показывает прошедшее время
- Границы дня берутся из `config.workday` (по умолчанию 10:00–20:00)

### Сервис напоминаний (`src/services/reminders.js`)

**Cron-задачи:**

1. **Напоминания за день записи** — в 08:00 по таймзоне салона, отправляет напоминание клиентам о записях на завтра (между сообщениями используется задержка ~500 мс).
2. **Напоминание за 2 часа** — проверка каждые 5 минут, окно 115–125 минут до начала (между сообщениями используется задержка ~500 мс); защита от дублей реализована через in‑memory Set `twoHourRemindedIds`.
3. **Автоматическое завершение записей** — проверка каждые 30 минут, статус меняется на "исполнено" сразу после окончания времени услуги.
4. **Очистка кэша напоминаний** — каждый день в 00:00 UTC очищает in‑memory Set `twoHourRemindedIds` (сброс одноразовых 2‑часовых напоминаний).
5. **Напоминания 28 дней** — ежедневно в 11:00 по таймзоне салона, с задержкой ~500 мс между сообщениями. Использует оптимизированный алгоритм: проверяет поле `Последняя_запись_UTC` из таблицы клиентов (O(n) сложность вместо O(n\*m)), исключает клиентов с активными записями через быструю проверку через Set.
6. **Ночная очистка сессий** — ежедневно в 02:00 по таймзоне салона выполняется очистка `sessions.json`: удаляются только сессии без активности более 30 дней, а общее количество записей ограничивается последними 150 по активности (активные/недавние сессии и текущие незавершённые диалоги не затрагиваются).
7. **Ежемесячная ротация записей в архив** — 1-го числа каждого месяца в 3:00 ночи автоматически переносятся записи старше 2 месяцев из листа `Записи` в лист `Записи_Архив`.

Для всех cron‑задач используется простая блокировка (флаги `cronLocks`), чтобы не запускать одну и ту же задачу повторно, если предыдущий запуск ещё не завершился.

### Бот (`src/bot/index.js`)

**Обработчики команд:**

- `/start` — приветствие и главное меню
- `/book` — запуск сцены записи
- `/services` — список услуг и длительностей
- `/cancel` — отмена сцены, сброс состояния
- `Мои записи` — показ будущих записей с кнопкой отмены
- `Записаться 💇‍♂️` — запуск сцены записи

**Inline-кнопки:**

- Отмена конкретной записи: `cancel_app:{id}`

**Сессии:** Хранятся в `sessions.json` через `telegraf-session-local`. При старте бота очищаются застрявшие сцены.

**Обработка ошибок:** Критические отправки сообщений (уведомления менеджеру, уведомления пользователям об отмене записей) используют `safeSendMessage` для предотвращения краха бота при ошибках Telegram API.

### Сцена записи (`src/bot/scenes/bookingScene.js`)

Wizard‑сцена с 6 шагами:

1. **Выбор услуги** — клавиатура с названиями услуг
2. **Выбор даты** — инлайн‑кнопки (календарь). Правила календаря:

- отображаются только даты текущего месяца;
- начиная с 15‑го числа текущего месяца дополнительно открывается следующий месяц;
- прошедшие дни не отображаются (учитывается таймзона салона).

3. **Выбор времени** — доступные слоты (по 4 в ряд)
4. **Имя** — текстовый ввод
5. **Контакт** — кнопка `Отправить контакт 📱`
6. **Комментарий** — опционально ( `-` для пропуска)
7. **Подтверждение** — инлайн‑кнопки ✅/❌

Навигация «Назад» реализована на шагах выбора даты и времени. Кнопки навигации (стрелки переключения месяцев) и выбор дат блокируются для неразрешённых месяцев.

**Обработка ошибок:** Уведомление менеджеру о новой записи отправляется через `safeSendMessage`, что предотвращает крах бота, если менеджер заблокировал бота.

## Правила разработки

### Стиль кода

- **Язык комментариев:** Русский (проект уже содержит русские комментарии)
- **Именование:** camelCase для переменных и функций
- **Константы:** UPPER_SNAKE_CASE для перечислений (статусы, услуги)
- **Асинхронность:** async/await, без коллбэков
- **Обработка ошибок:** try/catch с логированием в `console.error`

### Тестирование

Модульные тесты отсутствуют. При добавлении функционала рекомендуется:

- Тестировать бизнес-логику (booking.js) отдельно от бота
- Мокировать Google Sheets API для юнит-тестов

### Graceful shutdown

Обрабатываются сигналы `SIGINT` и `SIGTERM` для корректной остановки бота.

### Обработка ошибок

**Глобальная обработка:**

- Обрабатываются сигналы `SIGINT` и `SIGTERM` для корректной остановки бота
- Глобальные обработчики `unhandledRejection` и `uncaughtException` перехватывают необработанные ошибки
- Ошибки Telegram API (403, 429, 400) обрабатываются без завершения процесса
- Критические ошибки логируются и завершают процесс с кодом 1

**Обработка ошибок отправки сообщений:**

- Все критические отправки сообщений используют `safeSendMessage`/`safeSendPhoto` из `src/utils/safeMessaging.js`
- Ошибки 403 (пользователь заблокировал бота) логируются как предупреждения, не прерывают работу
- Ошибки 429 (превышен лимит) логируются с информацией о времени повтора
- Ошибки 400 (неверный запрос) логируются как предупреждения
- Все ошибки логируются в консоль с деталями для отладки

### Безопасность

- **Не коммитить:** `.env`, `credentials.json`, `sessions.json`
- **Сервисный аккаунт:** Должен иметь права Editor на Google Sheet
- **Приватный ключ:** В `.env` символы новой строки экранируются как `\n`

## Частые сценарии доработок

### Добавление новой услуги

1. Добавить запись в `SERVICES` в `src/services/booking.js`
2. Обновить сообщение в сцене (если нужно кастомное название)

### Изменение рабочих часов

Отредактировать `config.workday` в `src/config/index.js` или добавить переменную окружения.

### Добавление новой cron-задачи

Добавить в `src/services/reminders.js` по аналогии с существующими. Учитывать таймзону в `cron.schedule()`.

### Изменение структуры Google Sheets

1. Обновить `HEADERS` в `src/services/googleSheets.js`
2. Обновить `SHEET_NAMES` при необходимости
3. При миграции существующей таблицы — добавить миграционный скрипт

### Ручной запуск архивирования

Для ручного запуска архивирования записей можно использовать экспортированные методы:

```javascript
// В коде или через админ-команду
await sheetsService.archiveOldAppointments(2); // архивировать записи старше 2 месяцев
await sheetsService.migrateExistingDataToArchive(2); // однократная миграция
```

### Изменение периода архивирования

Период хранения активных записей настраивается через константу `ARCHIVE_MONTHS` в `src/services/googleSheets.js` (по умолчанию 2 месяца). После изменения константы нужно перезапустить бота.

## Известные проблемы и технический долг

1. **Дублирование кода:** `src/config/index.js` идентичен `index.js` — требует рефакторинга
2. **Отсутствие тестов:** Нет юнит-тестов и интеграционных тестов
3. **Жёсткие таймауты:** Кэш Google Sheets — ~30 минут; значение зашито в коде и при необходимости меняется через константы TTL в `src/services/googleSheets.js`
4. **Обработка блокировок:** Только `status === "заблокировано"` считается блокировкой

## Изменения

### Январь 2026 — Оптимизация производительности через архивирование

- **Система архивирования записей:** Реализована автоматическая ротация записей для оптимизации производительности
  - Разделение на активные записи (последние 2 месяца) и архив (старше 2 месяцев)
  - Новый лист `Записи_Архив` с теми же колонками, что и `Записи`
  - Клиентские методы оптимизированы для чтения только из активных записей (диапазон A2:Q500)
  - Методы поиска ищут в обоих листах (сначала активные, потом архив)
  - Админские методы объединяют данные из обоих листов для полной истории
- **Автоматическая ротация:** Ежемесячно в 3:00 ночи (1-го числа) записи старше 2 месяцев автоматически переносятся в архив
- **Автоматическая миграция:** При первом запуске после обновления существующие записи старше 2 месяцев автоматически переносятся в архив
- **Производительность:** Клиентские операции ускорены в 3-5 раз (с 2-5 секунд до <1 секунды), использование памяти снижено с 20-30MB до 5-10MB

Изменённые файлы:

- [src/services/googleSheets.js](src/services/googleSheets.js) — добавлена система архивирования, оптимизированы методы чтения, добавлены методы `archiveOldAppointments()` и `migrateExistingDataToArchive()`, добавлена крон-задача для ротации

### Январь 2026 — Админ-панель

- Добавлена админ‑панель: режим администратора теперь доступен командой `/admin` и отключается командой `/user`. В админ‑режиме интерфейс показан как reply‑клавиатура, визуально совпадающая с пользовательской.
- Клавиши админа: `Просмотр записей`, `Статистика`, `Отменить запись (по коду)`, `Забанить пользователя`, `Разбанить пользователя`, `Массовая рассылка`, `Вернуться в пользовательский режим`.
- Добавлена проверка `ctx.session.mode === 'admin'` — текстовые вводы для действий админа обрабатываются только в админ‑режиме.
- Реализована предпросмотр и подтверждение массовых рассылок (preview + confirm/cancel). Рассылка фильтрует клиентов по наличию `telegramId` и исключает забаненных.
- Добавлен сервис `src/services/admin.js` — управление банами (`banUser`, `unbanUser`, `isBanned`, `getBans`) и функция `broadcastToClients`.
- Расширен `src/services/googleSheets.js` методом `getAllClients()` для получения списка клиентов (используется при рассылках и поиске по username).

Изменённые файлы:

### Январь 2026 — Обработка ошибок отправки сообщений

- **Утилита безопасной отправки сообщений:** Создан модуль `src/utils/safeMessaging.js` с функциями `safeSendMessage`, `safeSendPhoto` и `safeReply` для безопасной отправки сообщений с обработкой ошибок Telegram API.
- **Глобальные обработчики ошибок:** Добавлены обработчики `unhandledRejection` и `uncaughtException` в `index.js` для перехвата необработанных ошибок. Ошибки Telegram API (403, 429, 400) обрабатываются без завершения процесса.
- **Улучшенная обработка ошибок:**
  - Все напоминания в `src/services/reminders.js` используют `safeSendMessage`
  - Рассылки в `src/services/admin.js` используют `safeSendMessage` и `safeSendPhoto`
  - Уведомления менеджеру в `src/bot/index.js` и `src/bot/scenes/bookingScene.js` используют `safeSendMessage`
  - Уведомления пользователям об отмене записей используют `safeSendMessage`
- **Типы обрабатываемых ошибок:**
  - **403 Forbidden** — пользователь заблокировал бота (логируется как предупреждение)
  - **400 Bad Request** — неверный запрос (логируется как предупреждение)
  - **429 Too Many Requests** — превышен лимит (логируется с информацией о времени повтора)
  - Другие ошибки логируются с деталями

### Январь 2026 — Оптимизация напоминаний за 28 дней

- **Оптимизация алгоритма поиска клиентов:** Функция `getClientsFor28DayReminder()` переписана для использования поля `Последняя_запись_UTC` из таблицы клиентов как основного источника данных
  - Убран неэффективный перебор всех записей из активных и архивных листов (O(n\*m) → O(n))
  - Добавлены быстрые фильтры в начале проверки (telegramId, banned, reminder28DaySentAtUtc)
  - Проверка активных записей выполняется через Set для O(1) поиска
  - Используется только `getAllActiveAppointments()` вместо `getAllAppointmentsFromBothSheets()`
- **Синхронизация данных:** При завершении записи (статус "исполнено") автоматически обновляется поле `Последняя_запись_UTC` в таблице клиентов через `updateAppointmentStatus()`
- **Улучшенная тестируемость:** Для тестирования достаточно изменить поле `Последняя_запись_UTC` в таблице клиентов, без необходимости изменения дат в завершенных записях
- **Производительность:** Система эффективно работает даже при 1000+ клиентов и 10000+ записей, время выполнения сокращено с нескольких секунд до <1 секунды
